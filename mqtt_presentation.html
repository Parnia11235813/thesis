چرا «فقط پیاده‌سازی حمله و دفاع» کافی نیست

در یک کارخانه‌ی صنعتی، ده‌ها سنسور کم‌توان از طریق پروتکل سبک MQTT با یک بروکر مرکزی حرف می‌زنند. اگر مهاجمی داده جعل کند یا سیستم را با سیل پیام غرق کند، نتیجه از یک هشدار اشتباه تا توقف خط تولید است. می‌شد گفت: «همیشه هر سه دفاع را روشن نگه دار»، اما هر دفاع هزینه دارد: پردازش، تأخیر، پیچیدگی. مدافع باید تصمیم بگیرد کدام ترکیب دفاعی می‌ارزد، در حالی‌که مهاجم هم عاقلانه و با توجه به هزینه‌ی خودش بهترین حمله را انتخاب می‌کند. این دقیقاً جایی‌ست که نظریه‌بازی‌ها لازم می‌شود.

۰۲ / پیاده‌سازی

توپولوژی و تبادل پروتکلی

چهار گره روی یک لینک CSMA مشترک با پشته‌ی کامل TCP/IP. تصمیم امنیتی بروکر همیشه بر پایه‌ی هویت اتصال (IP مبدأ در لحظه‌ی Accept) گرفته می‌شود، نه محتوای payload که در دنیای واقعی قابل جعل است.

PUBLISH(topic, QoS1, PacketId) → بروکر → PUBACK؛ در صورت پذیرش، forward به مشترک با PacketId تازه.

MQTT Wire

کدگذاری/کدگشایی بایت‌به‌بایت CONNECT/CONNACK/PUBLISH/PUBACK/SUBSCRIBE/SUBACK و بازآرایی جریان TCP.

۰۲

Research Payload

۱۲ بایت متادیتای تحقیقاتی (publisherId + sequence) داخل payload اپلیکیشن، بدون انحراف از استاندارد.

۰۳

Scenario State

تعریف انواع حمله، ~۳۰ شمارنده‌ی چرخه‌ی حیات پیام، rate limiter پنجره‌ی ثابت.

۰۴

Publisher

سنسور صنعتی قانونی: تولید ترافیک baseline با نرخ ثابت، بدون آگاهی از حمله/دفاع.

۰۵

Attacker

یک تابع واحد که بر اساس نوع حمله شاخه می‌رود؛ زیرساخت مشترک برای مقایسه‌ی برابر است.

۰۶

Subscriber

نقطه‌ی پایانی تحویل و نقطه‌ی سنجش: تأخیر سرتاسری از این‌جا اندازه‌گیری می‌شود.

۰۷

Broker

قلب امنیتی: طبقه‌بندی بر اساس IP، پایپ‌لاین دفاعی سه‌مرحله‌ای، forwarding.

۰۸

Main / Orchestration

پارس آرگومان، اعتبارسنجی «زمان‌بندی منجمد»، ساخت توپولوژی، خروجی JSON ساختاریافته.

۰۳ / تهدید و دفاع

سه حمله، سه دفاع، یک پایپ‌لاین

هر دفاع مستقل روشن یا خاموش می‌شود؛ در مجموع ۸ ترکیب دفاعی ممکن (d0 تا dRID) وجود دارد. ترتیب اجرا در بروکر همیشه ثابت است، مستقل از این‌که کدام دفاع‌ها فعال‌اند.

حمله‌ها (A)

Replay (پخش مجدد)

یک پیام قانونیِ قبلاً «شنیده‌شده» با Packet Identifier تازه دوباره ارسال می‌شود؛ sequence عمداً تغییر نمی‌کند چون خودِ ماهیت replay است.

Injection (تزریق)

یک پیام کاملاً جدید و جعلی از یک هویت غیرمجاز (publisherId=999) مستقیماً به بروکر فرستاده می‌شود.

DoS (منع سرویس)

یک دستگاه compromise‌شده با هویت معتبر، سیل پیام با نرخ بالا می‌فرستد تا ترافیک قانونی هم‌رتبه رد شود.

دفاع‌ها (D)

Auth / ACL

بروکر فقط به دستگاه‌های شناخته‌شده اجازه‌ی publish می‌دهد؛ تنها دفاعی که مستقل از نوع حمله عمل می‌کند.

Freshness / Anti-Replay

بالاترین sequence دیده‌شده به‌ازای هر ناشر قانونی نگه‌داری می‌شود؛ پیام با sequence قدیمی‌تر یا مساوی رد می‌شود.

Rate Limiting

پنجره‌ی ثابت‌یک‌ثانیه‌ای؛ حداکثر تعداد پیام مجاز از هر منبع را محدود می‌کند؛ ابزار اصلی مقابله با DoS است.

دریافت PUBLISH→ PUBACK بی‌قیدوشرط (سطح وایر)→ Auth / ACL→ Freshness→ Rate Limiting→ Forwarding به مشترک

روی یک سناریو بزنید تا مسیر واقعیِ همان پیام، از گره‌ی مبدأ تا نتیجه‌ی نهایی، قدم‌به‌قدم نشان داده شود. برای سناریوی DoS می‌توانید شدت حمله را هم با اسلایدر تغییر دهید.

۱لایه‌ی وایر MQTT

mqtt-wire.cc/h · TryExtractPacket
پیش‌زمینه و مفهوم: تنها مسئولیت این ماژول، کدگذاری و کدگشایی بایت‌به‌بایت پروتکل MQTT 3.1.1 است (CONNECT/CONNACK/PUBLISH/PUBACK/SUBSCRIBE/SUBACK). هیچ منطق امنیتی یا تحقیقاتی در آن نیست. فیلد «Remaining Length» در MQTT با یک عدد صحیح متغیرالطول (variable-byte integer) کدگذاری می‌شود: هر بایت ۷ بیت داده و ۱ بیت «ادامه دارد» حمل می‌کند، پس طول بسته می‌تواند بین ۱ تا ۴ بایت باشد، بدون این‌که برای پیام‌های کوچک فضای اضافه هدر برود.

دلیل جداسازی این ماژول: این عمدی است تا تغییر قوانین امنیتی در ماژول بروکر هرگز نیازی به دست‌کاری نحوه‌ی کدگذاری بایت‌ها نداشته باشد، و برعکس. 
bool
TryExtractPacket(std::vector<uint8_t>& stream, PacketView& out)
{
    if (stream.size() < 2) return false;

    uint32_t remainingLength = 0;
    size_t remainingLengthBytes = 0;
    if (!DecodeRemainingLength(stream, 1, remainingLength, remainingLengthBytes))
        return false; // incomplete TCP stream, wait for more bytes

    const size_t fullPacketBytes = 1 + remainingLengthBytes + remainingLength;
    if (stream.size() < fullPacketBytes) return false;

    out.header = stream[0];
    out.type = static_cast<uint8_t>((stream[0] >> 4) & 0x0f);
    out.body.assign(stream.begin() + (1 + remainingLengthBytes),
                     stream.begin() + fullPacketBytes);

    stream.erase(stream.begin(), stream.begin() + fullPacketBytes);
    return true;
}
چون TCP یک جریان بایت پیوسته است، نه پیام‌بندی‌شده، این تابع بافر دریافتی را می‌خواند و فقط وقتی یک پکت کامل در آن حاضر باشد استخراجش می‌کند؛ در غیر این صورت false برمی‌گرداند تا منتظر بایت‌های بیشتر بماند. این دقیقاً مشکل fragmentation/coalescing در TCP را حل می‌کند که خیلی از شبیه‌سازی‌های ساده آن را نادیده می‌گیرند.

۲Payload تحقیقاتی

research-payload.cc/h · CreateResearchPayload
MQTT فقط یک پاکت‌بندی است و به محتوای پیام کاری ندارد. این ماژول یک فرمت ۱۲بایتی (۴ بایت شناسه‌ی ناشر و ۸ بایت شماره‌ترتیب) تعریف می‌کند تا هر پیام دریافتی بعداً به منبعش نسبت داده شود؛ زیرساخت لازم برای محاسبه‌ی تأخیر سرتاسری و تشخیص Replay. 
std::vector<uint8_t>
CreateResearchPayload(uint32_t publisherId, uint64_t sequence, uint32_t payloadBytes)
{
    std::vector<uint8_t> payload;
    payload.reserve(12 + payloadBytes);

    WriteU32(payload, publisherId);
    WriteU64(payload, sequence);

    for (uint32_t i = 0; i < payloadBytes; ++i)
        payload.push_back(static_cast<uint8_t>(i & 0xff));

    return payload;
}
این ۱۲ بایت جزو هدر MQTT نیستند، کاملاً داخل Application Message payload قرار دارند؛ پس انحرافی از استاندارد وایر محسوب نمی‌شود، دقیقاً مثل یک سنسور صنعتی واقعی که JSON یا Protobuf داخل payload خودش می‌فرستد.

۳وضعیت مشترک سناریو

scenario-state.cc/h · RateLimitAccept
پیش‌زمینه و مفهوم: این ماژول تعریف بازی را نگه می‌دارد: نوع حمله‌ی جاری، کدام دفاع‌ها فعال‌اند، و همه‌ی شمارنده‌های اندازه‌گیری (حدود ۳۰ شمارنده که چرخه‌ی حیات هر پیام را دنبال می‌کنند). Rate limiter هم همین‌جا پیاده شده و بر پایه‌ی الگوریتم «شمارنده‌ی پنجره‌ی ثابت» (fixed-window counter) کار می‌کند: زمان پیوسته با تابع floor به بازه‌های صحیح یک‌ثانیه‌ای شکسته می‌شود (windowIndex = ⌊now⌋)؛ هر بازه یک شمارنده‌ی مستقل دارد که با ورود به بازه‌ی بعدی صفر می‌شود.

دلیل انتخاب این الگوریتم: ساده‌ترین و کم‌هزینه‌ترین روش پیاده‌سازی محدودسازی نرخ است (فقط یک متغیر شمارنده و یک اندیس زمانی)، اما هزینه‌اش این است که در مرز دو پنجره (مثلاً میلی‌ثانیه‌ی آخر یک ثانیه و میلی‌ثانیه‌ی اول ثانیه‌ی بعد) از نظر تئوری می‌تواند نزدیک به دو برابر نرخ مجاز عبور کند؛ جایگزین دقیق‌تر الگوریتم «پنجره‌ی لغزان» (sliding-window) است که این مرز را ندارد اما پیاده‌سازی پیچیده‌تری می‌طلبد. 
bool
RateLimitAccept(bool isAttack)
{
    if (!isAttack || !g_rateLimitingEnabled) return true;
    if (g_rateLimitHz <= 0.0) return false;

    const int64_t windowIndex =
        static_cast<int64_t>(std::floor(Simulator::Now().GetSeconds()));

    if (windowIndex != g_currentRateWindow)
    {
        g_currentRateWindow = windowIndex;
        g_rateWindowAccepted = 0;
    }

    const uint64_t maxAcceptedPerWindow =
        static_cast<uint64_t>(std::floor(g_rateLimitHz));

    if (g_rateWindowAccepted < maxAcceptedPerWindow)
    {
        ++g_rateWindowAccepted;
        return true;
    }
    return false;
}
پیاده‌سازی یک fixed-window rate limiter است، نه sliding-window: هر ثانیه (بر پایه‌ی floor(now)) یک پنجره‌ی تازه شروع می‌شود و حداکثر floor(rateLimitHz) پیام در آن پذیرفته می‌شود؛ در مرز دو پنجره، از نظر تئوری امکان یک burst لحظه‌ای بیش از نرخ مجاز وجود دارد.

۴ناشر

mqtt-publisher.cc/h · SendLegitimatePublish
نماینده‌ی دستگاه IoT صنعتی قانونی است: با نرخ ثابت تله‌متری می‌فرستد، کاملاً بی‌خبر از این‌که چه حمله یا دفاعی فعال است. تنها استثنا: اگر سناریوی Replay فعال باشد، همین‌جا لحظه‌ی انتشار پیامِ هدف «شنود» می‌شود. 
void
SendLegitimatePublish()
{
    if (Simulator::Now() >= g_trafficStop) return;

    const uint64_t sequence = g_nextLegitSequence++;
    const std::vector<uint8_t> payload =
        CreateResearchPayload(LEGITIMATE_PUBLISHER_ID, sequence, g_payloadBytes);

    if (g_attackKind == AttackKind::REPLAY &&
        !g_replayPayloadCaptured && sequence == g_replaySequence)
    {
        g_capturedReplayPayload = payload; // attacker "overhears" this message
        g_replayPayloadCaptured = true;
    }

    g_publisherSocket->Send(Mqtt::ToNs3Packet(Mqtt::BuildPublishQos1(
        MQTT_TOPIC, NextPacketId(g_nextPublisherPacketId), payload)));

    Simulator::Schedule(g_publishInterval, &SendLegitimatePublish);
}
تابعی خودزمان‌بند است که تا g_trafficStop خودش را دوباره زمان‌بندی می‌کند. نکته‌ی ظریف: capture پیام برای Replay دقیقاً همین‌جا، درون مسیر ترافیک قانونی، اتفاق می‌افتد؛ نه در ماژول مهاجم.

mqtt-attacker.cc/h · SendAttackMessage
هر سه حمله (Replay/Injection/DoS) از یک تابع واحد شاخه می‌روند تا زیرساخت مشترک (اتصال، PacketId، ارسال) داشته باشند و فقط در محتوای payload و زمان‌بندی فرق کنند؛ همین یکسان‌سازی، مقایسه‌ی apples-to-apples بین سه حمله را در نتایج ممکن می‌کند. 
if (g_attackKind == AttackKind::REPLAY)
{
    payload = g_capturedReplayPayload; // same sequence, fresh Packet Identifier
}
else if (g_attackKind == AttackKind::INJECTION)
{

{
    publisherId = LEGITIMATE_PUBLISHER_ID;

Replay و DoS از هویت «قانونی» استفاده می‌کنند (یکی پیام واقعی را تکرار می‌کند، دیگری از دستگاهی سازش‌شده با هویت معتبر می‌آید)، در حالی که Injection از یک هویت جعلی (۹۹۹) استفاده می‌کند که هرگز مجاز به CONNECT نبوده.

    ++g_state.unexpectedPackets;

پیش‌زمینه و مفهوم: قلب امنیتی سیستم. سه دفاع (Auth/ACL، Freshness، Rate Limiting) دقیقاً این‌جا به‌صورت یک پایپ‌لاین ترتیبی پیاده می‌شوند و تصمیم می‌گیرند پیام دریافتی forward شود یا نه. مبنای این طراحی یک اصل شناخته‌شده در مهندسی امنیت است: تصمیم امنیتی باید روی «مرز اعتماد» قابل‌تأیید بگیرد، نه روی داده‌ای که خودِ طرف مقابل تولید کرده. آدرس IP مبدأ یک اتصال TCP توسط پشته‌ی شبکه (نه توسط کلاینت) تعیین می‌شود، پس جعل آن در این مدل شبیه‌سازی ممکن نیست؛ محتوای payload اما کاملاً در کنترل فرستنده است.

دلیل این طراحی: اگر بروکر تصمیم امنیتی را از فیلد publisherId داخل payload می‌گرفت، یک مهاجم می‌توانست به‌سادگی همان شناسه‌ی قانونی را در پیام خودش بنویسد و از هر دفاعی عبور کند؛ چون تصمیم از روی IP اتصال گرفته می‌شود، این راه دور زدن دفاع اصلاً وجود ندارد. 
void
BrokerAccept(Ptr<Socket> socket, const Address& from)
{
    g_brokerClientRole[socket] = ClientRole::UNKNOWN;

    if (InetSocketAddress::IsMatchingType(from))
    {
        const InetSocketAddress remote =
            InetSocketAddress::ConvertFrom(from);

        if (remote.GetIpv4() == g_publisherIp)
            g_brokerClientRole[socket] = ClientRole::PUBLISHER;
        else if (remote.GetIpv4() == g_subscriberIp)
            g_brokerClientRole[socket] = ClientRole::SUBSCRIBER;
        else if (remote.GetIpv4() == g_attackerIp)
            g_brokerClientRole[socket] = ClientRole::ATTACKER;
    }
}

۱نرمال‌سازی تأخیر

stackelberg_extended_analysis.py · normalized_delay
پیش‌زمینه: تأخیر خام (میلی‌ثانیه) یک کمیت نامحدود است (نظراً می‌تواند هر عددی باشد)، در حالی که بقیه‌ی معیارهای مدل مثل (۱−PDR) یا F_B ذاتاً بین ۰ و ۱ محدودند. برای این‌که بشود این سه کمیت را با هم در یک فرمول واحد جمع کرد، باید تأخیر هم به همان بازه‌ی [۰،۱] نگاشته شود.

مفهوم ریاضی: ابتدا افزایش نسبی تأخیر نسبت به خط‌مبنای بدون‌حمله محاسبه می‌شود: δ = max(0, (D−D0)/D0)؛ یعنی δ می‌گوید تأخیر چند برابر حالت عادی بیشتر شده. سپس این مقدار نامحدود از تابع f(δ) = δ/(1+δ) عبور می‌کند. این تابع در δ=۰ مقدار ۰ می‌دهد، با افزایش δ به‌طور یکنوا و پیوسته به ۱ میل می‌کند اما هرگز از آن رد نمی‌شود (چون δ/(1+δ) < 1 برای هر δ متناهی)، و مشتقش همیشه مثبت است، یعنی تأخیر بیشتر همیشه به شدت آسیب بیشتر یا مساوی ترجمه می‌شود، هرگز کمتر.

دلیل انتخاب همین فرم: نسبت به یک برش خطی ساده مثل min(δ,1)، تابع δ/(1+δ) یک گذار نرم (بدون ناپیوستگی در مشتق) دارد و برای تأخیرهای خیلی بزرگ هم اطلاعات نسبی باقی می‌گذارد، به‌جای اینکه صاف روی سقف ۱ بماند و سناریوهای بد را از خیلی‌بد تشخیص ندهد. 
D0_MS = 1.014581  # baseline mean delay, no attack

def normalized_delay(delay_ms: float) -> float:
    delta = max(0.0, (delay_ms - D0_MS) / D0_MS)
    return delta / (1.0 + delta)

D_HAT_NO_RL = normalized_delay(DELAY_NO_RL_MS)  # = 0.995008
D_HAT_RL    = normalized_delay(DELAY_RL_MS)     # = 0.588071
D0_MS و مقادیر تأخیر خام (DELAY_NO_RL_MS, DELAY_RL_MS) مستقیماً از میانگین‌گیری روی ماتریس ۲۴۰-اجرایی به‌دست آمده‌اند؛ یعنی این ثابت‌ها مصرف می‌شوند، نه اینکه در همین اسکریپت تولید شوند.

۲شدت آسیب DoS

stackelberg_extended_analysis.py · dos_severity
پیش‌زمینه: چرا یک متریک به‌تنهایی کافی نیست؟ اگر فقط از افت نرخ تحویل (PDR) استفاده شود، سناریویی که در آن پیام‌ها دیر می‌رسند ولی نهایتاً همه تحویل داده می‌شوند امتیاز آسیب صفر می‌گیرد، در حالی که تجربه‌ی عملیاتی واقعاً بدتر شده؛ اگر فقط از تأخیر استفاده شود، سناریوی «پیام کاملاً حذف‌شده» دیده نمی‌شود.

مفهوم ریاضی: S_D یک ترکیب خطی وزن‌دار (weighted linear combination) از سه کمیت مستقل است: (۱−PDR) برای پیام‌های کاملاً ازدست‌رفته، F_B برای نرخ رد‌شدن در پایپ‌لاین forwarding، و D̂ برای تأخیر نرمال‌شده (از کارت قبل). چون هر سه جزء بین ۰ و ۱ محدودند و وزن‌ها جمعشان ۱ می‌شود، این یک ترکیب محدب (convex combination) است، یعنی S_D همیشه در بازه‌ی [۰،۱] می‌ماند و قابل تفسیر به‌عنوان «کسری از حداکثر آسیب ممکن» است.

دلیل وزن‌دار بودن، نه میانگین ساده: وزن‌ها اجازه می‌دهند اهمیت نسبی هر بعد از آسیب، بسته به اولویت سازمانی، تنظیم شود؛ مثلاً یک کارخانه‌ی حساس به زمان‌واقعی می‌تواند w_D را بالاتر بگذارد. همین انعطاف‌پذیری پایه‌ی تحلیل حساسیت وزن DoS در بخش نتایج است. 
def dos_severity(weights: DosWeights, rate_limited: bool) -> float:
    if rate_limited:
        pdr, fb, d_hat = PDR_RL, FB_RL, D_HAT_RL
    else:
        pdr, fb, d_hat = PDR_NO_RL, FB_NO_RL, D_HAT_NO_RL

    return (
        weights.wP * (1.0 - pdr)
        + weights.wF * fb
        + weights.wD * d_hat
    )
rate_limited فقط تعیین می‌کند کدام سه‌تایی مقدار خام (PDR/F_B/D̂) استفاده شود؛ وزن‌ها همیشه از بیرون تزریق می‌شوند و در تحلیل حساسیت روی کل سیمپلکس (wP+wF+wD=۱) پیمایش می‌شوند.

۳تصویر بر مثلث CIA

stackelberg_extended_analysis.py · cia_projected_impact
پیش‌زمینه: مثلث CIA (Confidentiality، Integrity، Availability) یک چارچوب کلاسیک در امنیت اطلاعات است که هر تهدید را روی سه بعد مستقل ارزیابی می‌کند: آیا داده افشا شد (C)، آیا داده دستکاری یا جعل شد (I)، و آیا سرویس در دسترس ماند (A).

مفهوم ریاضی: این تابع یک نگاشت شرطی (piecewise) است: بسته به نوع حمله، همان عدد Φ خام (از dos_severity برای DoS، یا مقدار باینری ۰/۱ برای Replay و Injection) در وزن بعد مربوطه (w_I یا w_A) ضرب می‌شود. چون هر حمله فقط یک بعد را فعال می‌کند، این عملاً یک تصویر متعامد (orthogonal projection) روی زیرفضای همان بعد است، نه ترکیب هم‌زمان چند بعد.

دلیل این نگاشت: Replay و Injection هر دو نوعی «جعل یا تکرار داده» هستند، پس مفهوماً یکپارچگی (Integrity) داده را نقض می‌کنند؛ DoS چون سرویس را از دسترس خارج می‌کند، به دسترس‌پذیری (Availability) نگاشت می‌شود. هیچ حمله‌ای در این پروژه محرمانگی را هدف نگرفته (چون هیچ داده‌ای استراق‌سمع یا افشا نشده)، پس w_C هرگز در این فرمول ضرب نمی‌شود؛ این یک محدودیت دامنه‌ی آگاهانه است، نه یک باگ. 
def cia_projected_impact(defense, attack, dos_weights, cia) -> float:
    """
    AR, AI -> Integrity
    AD     -> Availability
    Confidentiality -> no direct simulated loss in current attack set
    """
    phi = base_impact(defense, attack, dos_weights)

    if attack == "A0":
        return 0.0
    if attack in ("AR", "AI"):
        return cia.wI * phi
    if attack == "AD":
        return cia.wA * phi
بعد Confidentiality در این تابع اصلاً ظاهر نمی‌شود؛ چون هیچ حمله‌ای به محرمانگی شبیه‌سازی نشده، وزن wC در این نگاشت هرگز ضرب نمی‌شود. این یک محدودیت دامنه‌ی صریح و آگاهانه است، نه یک باگ.
۰۷ / لایه‌ی سوم

بازی Stackelberg: مدافع رهبر، مهاجم پیرو

مدافع اول ترکیب دفاعی‌اش را متعهد و آشکار می‌کند (مثل یک فایروال که روشن بودنش قابل‌کشف است). مهاجم با دیدن آن، بهترین پاسخ خودش را انتخاب می‌کند. تعادل نقطه‌ای‌ست که مدافع دیگر با تغییر یک‌طرفه‌ی تصمیمش وضعیت بهتری نمی‌گیرد. U_D = −Φ − C_D(d) , U_A = Φ − C_A(a)

(d*, a*) = (d_RID, A_D) تعادل مرجع در سناریوی هزینه‌ی پایه

در هزینه‌های مرجع، مدافع عقلانی هر سه دفاع را هم‌زمان مستقر می‌کند (dRID) و مهاجم عقلانی هم DoS را انتخاب می‌کند (A_D)، نه Replay یا Injection که هر دو با دفاع مربوطه کاملاً خنثی می‌شوند. این نقطه، خودِ سه لایه‌ی پروژه (پروتکل → Impact → بازی) را به یک عدد قابل‌دفاع می‌رساند.

پیاده‌سازی، بر اساس اسکریپت حل بازی

۱مطلوبیت مدافع و مهاجم

stackelberg_extended_analysis.py · attacker/defender_utility
پیش‌زمینه و مفهوم ریاضی: در نظریه‌ی بازی‌ها، مطلوبیت (Utility) عددی است که هر بازیگر تلاش می‌کند آن را بیشینه کند و بیانگر ارزش خالص یک پیامد برای اوست. اینجا هر دو تابع از یک مقدار مشترک، یعنی Φ (شدت آسیب پیش‌بینی‌شده، محاسبه‌شده در لایه‌ی دوم)، تغذیه می‌شوند، اما با علامت مخالف: مهاجم آسیب را سود خودش می‌بیند (Φ منهای هزینه‌ی حمله)، مدافع همان آسیب را زیان خودش می‌بیند (منفی Φ منهای هزینه‌ی دفاع). این یعنی بخش Φ تقریباً حاصل‌جمع‌صفر است، اما چون هزینه‌ی حمله C_A و هزینه‌ی دفاع C_D مستقل و نامتقارن‌اند، کل بازی حاصل‌جمع‌صفر واقعی نیست.

دلیل این طراحی: ترکیب خطی (تفریق ساده به‌جای وزن‌دهی غیرخطی یا ضرب) عمداً انتخاب شده تا اثر هر تغییر در هزینه روی نتیجه‌ی نهایی، قابل ردیابی و قابل تفسیر بماند؛ همین سادگی است که تحلیل‌های حساسیت بخش بعدی (تغییر وزن‌ها و آستانه‌ها) را ممکن می‌کند. 
def attacker_utility(defense, attack, costs, dos_weights, cia=None) -> float:
    phi = cia_projected_impact(defense, attack, dos_weights, cia) \
          if cia else base_impact(defense, attack, dos_weights)
    return phi - attack_cost(attack, costs)

def defender_utility(defense, attack, costs, dos_weights, cia=None) -> float:
    phi = cia_projected_impact(defense, attack, dos_weights, cia) \
          if cia else base_impact(defense, attack, dos_weights)
    return -phi - defense_cost(defense, costs)
هر دو تابع از همان Φ محاسبه‌شده در لایه‌ی Impact استفاده می‌کنند؛ فقط علامت و جمله‌ی هزینه فرق دارد. این یعنی هر تغییر در مدل Impact، خودکار در نتیجه‌ی بازی هم اثر می‌گذارد، بدون نیاز به هماهنگی دستی.

پیش‌زمینه و مفهوم ریاضی: بازی Stackelberg یک بازی رهبر پیرو (Leader Follower) است: رهبر (مدافع) راهبرد خود را اول و به‌صورت متعهدانه اعلام می‌کند، پیرو (مهاجم) آن را می‌بیند و بهترین پاسخ خودش را انتخاب می‌کند. روش استاندارد حل چنین بازی‌ای، استقراء پسرو (Backward Induction) است: برای هر راهبرد ممکن مدافع، اول بهترین پاسخ مهاجم پیدا می‌شود، سپس مدافع از میان این پاسخ‌ها، راهبردی را انتخاب می‌کند که بیشترین مطلوبیت را برایش دارد. مسئله‌ی تساوی وقتی رخ می‌دهد که argmax مطلوبیت مهاجم یک مجموعه‌ی چندعضوی باشد، نه یک پاسخ یکتا؛ در این حالت رفتار مهاجم از دید مدافع قابل‌مشاهده نیست و دو قرارداد استاندارد در ادبیات بازی‌های امنیتی وجود دارد: تعادل قوی Stackelberg (SSE)، که خوش‌بینانه است و فرض می‌کند مهاجم در صورت تساوی، گزینه‌ای را انتخاب می‌کند که برای مدافع بهتر است، و تعادل ضعیف Stackelberg (WSE)، که بدبینانه است و بدترین حالت را برای مدافع در نظر می‌گیرد.

دلیل محاسبه‌ی هر دو قرارداد: چون این فرض رفتاری قابل‌مشاهده یا قابل‌اثبات نیست، محاسبه‌ی هر دو تعادل (SSE و WSE) نشان می‌دهد نتیجه‌ی نهایی چقدر به این فرض حساس است؛ همین مقایسه، پایه‌ی مستقیم تحلیل «استحکام تساوی‌شکن» در بخش بعد است. 
for d in feasible_defenses:
    au = {a: attacker_utility(d, a, costs, dos_weights, cia) for a in ATTACKS}
    br, _ = argmax_ties(au)              # attacker's best-response set
    attacker_br_sets[d] = br

    du = {a: defender_utility(d, a, costs, dos_weights, cia) for a in br}

    if tie_break == "strong":
        a_star = max(br, key=lambda a: (du[a], a))
    elif tie_break == "weak":
        a_star = min(br, key=lambda a: (du[a], a))

    chosen_attack[d] = a_star
    leader_values[d] = du[a_star]

d_star, value = argmax_ties(leader_values)   # leader's best defense(s)
تساوی در بهترین‌پاسخ پیرو یک اتفاق واقعی در این بازی است، نه یک حالت لبه‌ای نادر؛ به همین دلیل کد آن را صریح مدیریت می‌کند، به‌جای انتخاب خاموش یکی از گزینه‌های مساوی. همین انتخاب صریح است که در بخش بعد، پایه‌ی تحلیل «استحکام تصمیم» می‌شود.

نقاط ضعف واقعی و مرزهای دامنه‌ی پروژه

این محدودیت‌ها آگاهانه و از ابتدای طراحی پروژه شناخته‌شده بوده‌اند؛ هرکدام دلیل مشخصی دارد و مسیر رفعش در کار آینده مشخص است.

·

پیاده‌سازی MQTT متمرکز بر wire-format است، نه یک بروکر تولیدی کامل (بدون session persistence، retained messages، wildcard).

·

مدل Auth/ACL یک فلگ باینری است، نه سازوکار رمزنگاری‌شده‌ی واقعی؛ فضای دفاع نیز گسسته/باینری است.

·

توپولوژی و بار کاری تک‌حالته (یک ناشر، یک مشترک، یک لینک CSMA)، بدون بررسی حساسیت به مقیاس شبکه.

·

rate limiting از نوع fixed-window است، نه sliding-window؛ در مرز دو پنجره از نظر تئوری burst لحظه‌ای ممکن است.

·

هزینه‌های بازی نرمال‌شده‌اند و لنگری به دنیای واقعی (دلاری/عملیاتی) ندارند؛ گزارش آماری بر پایه‌ی ۱۰ تکرار در هر سلول است.

·

تحلیل «Adaptive» یک comparative statics تک‌بعدی است (فقط c_λ)، نه یادگیری تطبیقی واقعی مهاجم.

·

تعادل در بخش‌هایی (به‌ویژه بودجه) به قاعده‌ی تساوی‌شکن Strong/Weak حساس است؛ این یک فرض رفتاری است، نه واقعیت مشاهده‌شده.

·

بدون اعتبارسنجی مقابل یک broker واقعی (Mosquitto/HiveMQ) یا داده‌ی میدانی؛ بدون شبیه‌سازی حمله به محرمانگی.
